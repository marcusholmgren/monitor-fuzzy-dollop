# ADR 001: Data Layer, Storage Strategy, and Keyset Pagination Identifiers

## Status

Accepted

## Context

The system ingests sensor readings across ~300 houses and up to 3,000 sensors. Steady-state volume is approximately 1 million events per month, but an initial historical backfill (5–10 years of data) will stream out-of-order over several months via HTTP. There is no external broker (Kafka/Redis) available. The read API requires keyset (cursor-based) pagination sorted descending by time (`recorded_at DESC`), with optional filtering on `house_id` and `sensor_id`.

Key constraints:

* Out-of-order historical writes land across the entire timeline.
* Read queries must paginate deterministically without using offset/limit.
* Ingestion must skip duplicates (`ON CONFLICT DO NOTHING`).
* Raw throughput, asynchronous I/O, and low memory overhead are priorities, ruling out heavy ORM serialization.

## Decision

### 1. Database Access via `psycopg` (v3 Async)

We will use **psycopg 3** with `AsyncConnectionPool` instead of an ORM like TortoiseORM.

* **Rationale:** High-throughput batch inserts using `cursor.executemany()` or binary `COPY` via `psycopg` eliminate ORM model instantiation overhead and memory churn.
* **Idempotency:** Direct SQL enables clean `INSERT ... ON CONFLICT (sensor_id, recorded_at) DO NOTHING` semantics.

### 2. ID Generation: Standard UUIDv7 vs. KSUID

We will use **UUIDv7** (RFC 9562) as the surrogate primary key for readings, evaluated against KSUID:

* **Evaluation:** KSUID generates 20-byte identifiers (typically base62-encoded 27-character strings). This requires either custom 20-byte binary columns (`BYTEA`) or large `VARCHAR` columns in PostgreSQL, degrading B-Tree leaf density.
* **Why UUIDv7:** UUIDv7 embeds a millisecond-precision Unix timestamp in the leading 48 bits while conforming to the standard 16-byte `UUID` data type natively supported by PostgreSQL.
* **Index Locality & Cursor:** In conjunction with `recorded_at`, UUIDv7 guarantees deterministic tie-breaking for cursor pagination without extra storage overhead.

### 3. Keyset Pagination Scheme

Read queries will sort by `(recorded_at DESC, id DESC)`. The opaque cursor sent to clients will be a base64-encoded JSON payload:

```json
{"recorded_at": "2026-03-29T10:15:30.123456Z", "id": "018e88e8-..."}

```

Queries will filter via row comparison:

```sql
WHERE (recorded_at, id) < (%(cursor_time)s, %(cursor_id)s)

```

### 4. Indexing Strategy (Non-Partitioned Initial Phase)

Given standard B-Trees on non-partitioned PostgreSQL:

* Primary Key: `id UUID DEFAULT gen_random_uuid()` (or generated at app layer via UUIDv7).
* Unique Constraint: `UNIQUE (sensor_id, recorded_at)` to support `ON CONFLICT DO NOTHING`.
* Composite Index for Sensor queries: `CREATE INDEX idx_readings_sensor_time ON readings (sensor_id, recorded_at DESC, id DESC);`
* Composite Index for House queries: `CREATE INDEX idx_readings_house_time ON readings (house_id, recorded_at DESC, id DESC);`

## Consequences

### Positive

* Zero ORM footprint; maximum write throughput using parameterized async queries.
* UUIDv7 fits natively into PostgreSQL's 128-bit `uuid` type, minimizing index bloat relative to 20-byte/text KSUIDs.
* Tuple comparison `(recorded_at, id) < (...)` performs index range scans, avoiding `OFFSET` performance decay.

### Negative

* **Backfill Index Fragmentation:** Inserting 5–10 years of backfilled data means inserts will hit random leaves within the `recorded_at` B-Tree indexes, requiring adequate PostgreSQL buffer cache allocation (`shared_buffers`).
* Table partitioning may need to be retrofitted later if the table exceeds ~100M rows and query performance degrades.
